# WordPress版 本番公開・切り戻し・運用手順

## 目的と現在の前提

この文書は、Localで完成・検証したWordPress版を、ステージングを経由して本番公開し、障害時に安全に切り戻すための実行手順である。公開作業では、テーマ、プラグイン、データベース、アップロード、URL、SSLを一つのリリース単位として扱う。

2026-08-25時点では、本番サーバー、ドメイン、DNS管理者、公開日時、運用担当者が未確定のため、本番への変更操作は未実施である。Local側では、最新版WPvividバックアップを一時MySQLデータベースと一時WordPressへ実復元し、内部状態22項目、公開12 URL、管理者ログインを確認済みである。

現行サイトはポートフォリオ用の架空サイトであり、Forminatorは次のデモ設定を維持する。

- メール通知: 0件
- 送信データのDB保存: 無効
- honeypot: 有効
- 完了表示: メール送信・保存を行わない旨を表示
- 実在する個人情報: 入力禁止

実際の問い合わせ受付へ変更する場合は、送信先、Reply-To、SMTP、保存期間、閲覧権限、同意文、Turnstileを別案件として設計し、この公開手順へ混在させない。

## 3. ステージングへの復元

本番へ直接復元せず、先に本番相当のステージングで行う。

1. 空のWordPressと専用データベースを用意する。
2. 公式WPvivid Backup & Migrationをインストールして有効化する。WPvivid自身はバックアップへ含まれない。
3. 統合ZIPをWPvividへ登録し、WordPressファイルを復元してからDBを復元する。
4. 復元先DBの接続情報が異なる場合は`wp-config.php`を復元先に合わせる。
5. 旧URLからステージングURLへの置換を、まず`--dry-run`で確認する。

```bash
wp search-replace 'http://hidamari-care-asahikawa.local' 'https://staging.example.jp' \
  --all-tables-with-prefix --skip-columns=guid --dry-run
```

6. 件数と対象を確認してから、`--dry-run`だけを外して実行する。PHPのシリアライズデータを壊すため、SQLの単純文字列置換は使わない。
7. `home`、`siteurl`、パーマリンクを確認する。

```bash
wp option get home
wp option get siteurl
wp rewrite flush --hard
```

8. 復元した管理者パスワードを安全な値へ変更し、不要なセッションを終了する。バックアップ由来の一時ユーザーは残さない。
9. `wp-config.php`、バックアップZIP、SQL、ログをWeb公開領域から除外する。
10. 継続デプロイ方法を決める。Git管理するテーマ／サイト機能プラグインと、管理画面で更新するDB／メディアを相互に上書きしない。

URL置換にはシリアライズデータを扱えるWordPress公式の`wp search-replace`を使う。構文は [WP-CLI公式コマンド資料](https://developer.wordpress.org/cli/commands/search-replace/) を基準にする。

## 5. HTTPSと本番URL

1. DNS切替前に本番WebサーバーへSSL証明書を発行し、更新方式を確認する。
2. HTTPSの仮URLまたはhosts切替で、証明書チェーン、ホスト名、有効期限を確認する。
3. WordPressの`home`と`siteurl`を最終HTTPS URLへ変更する。
4. HTTPからHTTPSへの301リダイレクトを1回だけ実装し、ループがないことを確認する。
5. HTML、CSS、JavaScript、画像、フォント、canonical、OGP、サイトマップにHTTP混在がないことを確認する。
6. 管理画面とログインもHTTPSに限定する。`FORCE_SSL_ADMIN`は証明書とプロキシ設定が正しく動作した後に有効化する。
7. リバースプロキシやCDN利用時は、転送ヘッダーの扱いをホスティング仕様に合わせ、HTTPSリダイレクトループを確認する。
8. HSTSはHTTPS運用とサブドメイン影響を確認した後に段階導入し、初回公開と同時に長期間・`includeSubDomains`・preloadを設定しない。

WordPress公式も、HTTPS強制の前にSSLと仮想ホスト設定が必要で、リバースプロキシではループへ注意するよう案内している。詳細は [WordPress HTTPS資料](https://developer.wordpress.org/advanced-administration/security/https/) を参照する。

## 6. 公開当日の順序

1. 変更凍結時刻を宣言し、公開中サイトで新規投稿や設定変更を止める。
2. 公開直前のDB＋全ファイルバックアップを取得し、時刻、容量、SHA-256、保存先を記録する。
3. 現行本番がある場合は、現行本番側の独立バックアップも取得する。
4. ステージングで承認した同一セットを本番へ反映する。未確認のWordPress本体・プラグイン更新を同時に行わない。
5. 本番URLへシリアライズ対応のURL置換を実施し、`home`、`siteurl`、パーマリンクを確認する。
6. DNS変更が必要な場合は承認済みレコードだけを変更し、旧環境をすぐ削除しない。
7. HTTPSとHTTP→HTTPSリダイレクトを確認する。
8. 管理者ログイン、施設担当者ログイン、TOP、主要ページ、404、サイトマップを確認する。
9. 架空のダミーデータでデモフォームを1回確認し、通知0件、DB保存0件、完了文を再確認する。
10. title、description、canonical、OGP、robots、サイトマップ、faviconを確認する。
11. 物理スマートフォンでメニュー、FAQ、フォームを確認する。
12. PHP、Webサーバー、ブラウザーコンソール、監視通知を確認する。
13. 最終承認者が公開継続または切り戻しを判断し、時刻と判断を記録する。

## 7. 切り戻し条件と手順

次のいずれかが発生し、15分以内に安全な修正方針が確定しない場合は切り戻す。

- TOPまたは主要ページが5xx、白画面、無限リダイレクトになる
- 管理画面へ管理者がログインできない
- 固定ページ、投稿、FAQ、料金、フォーム設定、画像が欠落する
- HTTPS証明書、混在コンテンツ、canonical、robotsに公開継続できない問題がある
- 意図しないメール送信または個人情報保存が発生する
- 重大なPHP Fatal Error、DB接続エラー、セキュリティ問題が発生する

切り戻しは次の順で行う。

1. 更新操作を停止し、障害時刻、症状、変更内容を記録する。
2. 障害状態のDB、ファイル、ログを別名で保全する。原因調査前に上書きしない。
3. 公開直前に取得した同一世代のDB＋全ファイルを復元する。DBだけ、またはファイルだけを異なる時点へ戻さない。
4. `wp-config.php`、URL、パーマリンク、キャッシュを確認する。
5. DNS切替が原因の場合は、承認済みの旧レコードへ戻す。TTLによる反映時間を記録する。
6. TOP、主要ページ、管理者ログイン、デモフォーム設定、SEO、HTTPS、ログを再確認する。
7. 復旧時刻、復元したバックアップID・SHA-256、残る影響を関係者へ共有する。
8. 原因と再発防止がステージングで確認できるまで再公開しない。

## 8. バックアップと運用の初期案

運用責任者が別の基準を指定しない場合の初期案とする。

| 対象 | 頻度 | 保持 | 保存場所 |
|---|---|---|---|
| DB | 毎日 | 14世代 | ホスト外の暗号化ストレージを含む2か所以上 |
| DB＋全ファイル | 毎週 | 8世代 | ホスト外の暗号化ストレージを含む2か所以上 |
| 月次フルバックアップ | 毎月 | 12世代 | 長期保管先 |
| 更新・公開前スナップショット | 毎回 | 次回安定確認後も最低1世代保持 | 即時復元できる場所 |

バックアップ成功通知だけで復元可能とは判断しない。月1回はZIP読取、ハッシュ、DBパッケージを確認し、四半期ごと、またはWordPress／主要プラグインの大きな更新前後に別環境へ復元する。WordPress公式資料も、DBとファイルの両方、複数世代、別の場所への保管を推奨している。詳細は [WordPress Backups](https://developer.wordpress.org/advanced-administration/security/backup/) を参照する。

## 9. 更新、監視、セキュリティ

### 更新

- WordPress本体、外部テーマ、外部プラグインは、変更内容と互換性をステージングで確認してから本番へ反映する。
- 更新前にDB＋全ファイルのバックアップを取得する。
- 更新後は表示、ログイン、フォーム、SEO、サイトマップ、ログ、復元性を確認する。
- 使用しないプラグインとテーマは削除する。テーマとサイト機能プラグインのコードはGitを管理元とする。
- 本番管理画面からのテーマ／プラグインコード編集は無効化する。`DISALLOW_FILE_EDIT`はホスティング構成とデプロイ手順を確認して設定する。
- WordPressコアは `wp core verify-checksums`、WordPress.org配布プラグインは `wp plugin verify-checksums --all`を確認に使える。サイト固有プラグインはWordPress.orgのチェックサム対象外なのでGit差分で確認する。

公式の基本方針は、WordPress本体、テーマ、プラグインを更新し、権限・ファイル・バックアップ・監視を多層で管理することである。詳細は [Hardening WordPress](https://developer.wordpress.org/advanced-administration/security/hardening/) と [wp core verify-checksums](https://developer.wordpress.org/cli/commands/core/verify-checksums/) を参照する。

### 監視

- 5分間隔を目安にTOPのHTTP状態と応答時間を監視
- SSL期限を30日前、14日前、7日前に通知
- バックアップ失敗を当日中に通知
- PHP Fatal Error、DB接続エラー、5xx増加を通知
- WordPress本体・プラグインのセキュリティ更新を週1回以上確認
- ディスク容量、DB容量、バックアップ容量を月1回確認
- フォームを実運用へ変更した場合だけ、送信失敗、到達性、スパム、保存件数、削除期限を監視

### 月次レビュー

- 管理者・編集者・不要ユーザーと最終ログインを確認
- バックアップ世代、別保管、ハッシュ、復元テスト履歴を確認
- 更新保留、PHP／Webサーバーログ、404、サイトマップ、SEO、リンク切れを確認
- 正式データ、画像権利、デモ案内、プライバシーポリシーの整合を確認
- 実施内容、確認結果、残る課題を`HISTORY.md`または運用記録へ残す

## 10. 本番公開完了判定

次の条件がすべて満たされたときだけ、本番公開完了とする。

- [ ] 第1節の未確定情報と承認者がすべて確定
- [ ] ステージング完了条件をすべて満たす
- [ ] 正式原稿・連絡先・画像・サービス範囲、または架空デモ継続方針が承認済み
- [ ] 本番直前バックアップと現行本番バックアップを別場所に保管
- [ ] HTTPS、URL、リダイレクト、SEO、表示、フォーム、ログイン、権限を本番URLで確認
- [ ] 物理スマートフォンで最終操作確認
- [ ] 定期バックアップ、監視、更新、障害連絡、RPO／RTOを運用担当者が承認
- [ ] 切り戻し担当者が手順と復元対象を確認
- [ ] 最終承認者が公開継続を記録

未確定のまま残してよい項目はない。公開作業で新しい差分が出た場合は、その差分をステージングへ戻して確認してから再度判定する。
